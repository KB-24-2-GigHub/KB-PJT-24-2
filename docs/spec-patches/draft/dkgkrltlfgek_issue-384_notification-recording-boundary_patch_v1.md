# SPEC-384-01: 알림 적재 경계 — 트랜잭션 참여와 재실행 멱등

`SPEC-382-01`이 알림의 유형·수신자·응답 계약을, `SPEC-383-01`이 저장 불변식을 정합니다.
이 Patch는 그 둘이 정하지 않은 하나, **알림 적재가 원인 도메인 트랜잭션과 맺는 관계**만
정합니다.

`ALERT-002`는 "도메인 트랜잭션이 실패하면 알림을 확정하지 않는다"만 규정합니다. 반대 방향,
즉 알림 적재가 실패했을 때 정산·예치 같은 자금 트랜잭션을 어떻게 할지는 승인 계약에
없었고, 정하지 않으면 구현자마다 다르게 처리합니다.

## 추가 사항

### 트랜잭션 참여

- 알림 적재는 원인이 되는 도메인 트랜잭션에 **참여**합니다. 별도 트랜잭션으로 분리하거나
  트랜잭션 커밋 후로 미루지 않습니다.
- 중복 유일 제약 위반은 실패가 아닙니다. "이미 같은 이벤트의 알림이 있다"로 해석해 도메인
  트랜잭션을 계속 진행합니다.
- 그 밖의 알림 적재 실패는 원인 도메인 트랜잭션과 함께 되돌립니다. 알림만 조용히 유실되는
  경로를 두지 않습니다.
- 알림 적재는 외부 시스템 호출을 하지 않습니다. 저장 한 건 외에 트랜잭션을 길게 만드는
  작업을 붙이지 않습니다.

이 선택의 대가는 알림 저장 실패가 자금 트랜잭션을 되돌릴 수 있다는 것입니다. 그럼에도
참여를 택하는 이유는 두 가지입니다. 알림을 별도 트랜잭션으로 빼면 실패한 알림을 되살릴
재시도 경로가 이 MVP에 없어 유실이 그대로 확정되고, 되돌린 자금 트랜잭션은 부분 상태를
남기지 않아 사용자가 다시 시도할 수 있습니다.

### 재실행 멱등

- 같은 도메인 이벤트가 재시도, Scheduler 재실행, 중복 요청으로 여러 번 처리돼도 수신자당
  알림은 한 건입니다. 중복 판정은 애플리케이션 선검사가 아니라 `SPEC-383-01`의 유일
  제약으로 합니다.
- 수신자가 둘인 유형에서 한 수신자의 알림이 이미 있고 다른 수신자의 알림이 없으면, 없는
  쪽만 새로 만듭니다.

### 안읽음 개수

- 안읽음 개수는 0 미만이 될 수 없습니다.
- 이미 읽은 알림을 다시 읽음 처리해도 안읽음 개수가 변하지 않습니다.
- 안읽음 개수는 저장된 읽음 상태에서 계산하며 별도 집계 값을 따로 유지하지 않습니다.

## 완료 조건

- [ ] 알림 적재가 실패하면 원인 도메인 트랜잭션도 되돌아가고 부분 상태가 남지 않는다.
- [ ] 중복 유일 제약 위반은 도메인 트랜잭션을 되돌리지 않고 알림도 한 건만 유지한다.
- [ ] 도메인 트랜잭션이 실패하면 알림이 남지 않는다.
- [ ] 같은 이벤트를 두 번 처리해도 수신자당 알림이 한 건이다.
- [ ] 수신자 둘 중 한쪽 알림만 있는 상태에서 재처리하면 없는 쪽만 생성된다.
- [ ] 이미 읽은 알림을 다시 읽음 처리해도 안읽음 개수가 줄지 않고 음수가 되지 않는다.
- [ ] 안읽음 개수가 저장된 읽음 상태와 항상 일치한다.
