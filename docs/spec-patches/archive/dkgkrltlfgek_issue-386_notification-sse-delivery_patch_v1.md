# SPEC-386-01: 알림 실시간 전달 — 신호 전용 SSE 스트림

`SPEC-382-01`이 알림의 유형·수신자·응답 계약을, `SPEC-383-01`이 저장 불변식을,
`SPEC-384-01`이 적재 경계를 정합니다. 이 Patch는 그 위에 하나만 더합니다 —
**이미 적재된 알림을 사용자가 화면 새로고침 없이 알아차리는 전달 수단**입니다.

## 추가 사항

### 스트림은 신호만 전달하고 알림 계약을 새로 정의하지 않는다

- 서버는 새 알림이 적재된 수신자에게 "다시 조회하라"는 신호를 보냅니다. 알림의 본문, 유형,
  식별자를 스트림으로 내려보내지 않습니다.
- 알림의 내용은 `GET /api/notifications`와 `GET /api/notifications/unread-count`가 계속
  단독으로 소유합니다. 같은 알림이 두 가지 형태로 존재하지 않습니다.
- 신호는 **적재가 확정된 뒤에만** 보냅니다. 적재에 실패한 수신자에게는 보내지 않습니다.
  먼저 보내면 아직 조회되지 않는 알림을 가리키게 됩니다.

### 구독 대상은 인증 Principal이 정한다

- `GET /api/notifications/stream`은 인증 사용자 본인의 스트림만 엽니다.
- 사용자 식별자를 Request Parameter, Path, Body 중 어디로도 받지 않습니다. 받는 순간 타인의
  알림 발생 사실을 엿듣는 경로가 생깁니다.
- 미인증 요청은 다른 `/api/**`와 동일하게 `401 AUTH_REQUIRED`로 거절합니다.

### 실시간 전달은 알림 기능의 전제가 아니다

- 스트림 연결이 실패하거나 끊긴 동안에도 알림 목록 조회와 읽음 처리는 정상 동작합니다.
- 신호 전달 실패는 알림 적재 결과와 도메인 처리 결과를 바꾸지 않습니다. `SPEC-384-01`의
  "알림은 도메인 Commit을 되돌리지 않는다"가 그대로 유지됩니다.
- 신호를 놓쳤을 때의 관측 가능한 영향은 "화면을 다시 열어야 보인다"까지입니다. 알림 자체는
  저장돼 있으므로 유실되지 않습니다.

### 연결 수명은 서버가 명시적으로 관리한다

- 스트림 응답에는 중간 프록시의 응답 Buffering을 끄는 지시가 포함됩니다. 없으면 배포
  환경에서만 이벤트가 도달하지 않습니다.
- 서버는 조용한 구간에도 주기적으로 연결 유지 프레임을 보냅니다. 주기는 배포 프록시의 읽기
  타임아웃보다 충분히 짧아야 합니다.
- 연결 타임아웃은 애플리케이션이 명시합니다. 컨테이너 기본값에 맡기지 않습니다.
- 연결 종료·타임아웃·오류 어느 경로로 끊기든 서버는 해당 연결을 즉시 버립니다. 죽은 연결이
  남으면 연결 유지 프레임이 계속 그쪽으로 나갑니다.

### 한계 — 단일 인스턴스 전제

구독 연결을 애플리케이션 인스턴스 메모리에 유지합니다. 인스턴스가 둘 이상이면 다른
인스턴스에 연결된 사용자는 신호를 받지 못합니다. 이 한계는 위의 "실시간 전달은 전제가
아니다"로 흡수되며, 다중 인스턴스가 필요해지면 공유 Broker를 별도 이슈와 Patch로 도입해야
합니다.

## 완료 조건

- [ ] 인증 사용자가 자신의 알림 스트림만 구독하고, 타인 스트림 구독 경로가 없다.
- [ ] 새 알림이 적재된 수신자에게만 신호가 가고, 적재에 실패한 수신자에게는 가지 않는다.
- [ ] 스트림 응답이 프록시 Buffering을 끄는 지시를 포함한다.
- [ ] 조용한 구간에도 프록시 읽기 타임아웃보다 짧은 주기로 연결 유지 프레임이 나간다.
- [ ] 연결 타임아웃이 애플리케이션 코드에 명시돼 있다.
- [ ] 연결 종료·타임아웃·오류에서 서버가 그 연결을 더 이상 유지하지 않는다.
- [ ] 스트림 연결이 실패한 상태에서도 알림 목록 조회와 읽음 처리가 정상 동작한다.
- [ ] 신호 전달 실패가 알림 적재 결과와 도메인 응답을 바꾸지 않는다.
